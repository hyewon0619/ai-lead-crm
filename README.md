# AI Lead CRM

진행 중인 사건 기록에서 **고객의 새로운 법률 수요(리드)를 AI로 찾아내고**,
직원 제보와 함께 **리드 → 기회 → 선임**까지 한 흐름으로 관리하는 CRM입니다.

문제의식은 이렇습니다. 사건을 진행하다 보면 의뢰 고객이 지나가듯 다른 문제를 꺼냅니다.
"직원이 퇴직금 진정을 냈다", "세무조사 통지를 받았다" 같은 말이요. 이런 말은 사건 기록에
남지만, 담당자가 바쁘면 그대로 묻힙니다. 이 시스템은 그런 단서를 놓치지 않고 모아서
담당 부서 검토자에게 넘기고, 실제 선임으로 이어졌는지까지 추적합니다.

```
Python 3.11 · FastAPI · SQLAlchemy · MySQL · Elasticsearch(Nori)
React 19 · TypeScript · Tailwind CSS · Base UI · Vitest
```

> **공개본에 관하여**
> 실무에서 팀으로 개발·운영한 시스템(기여도 약 60%)을 공개용으로 다시 구현한 저장소입니다.
> 실제 사건·고객 데이터, 사내 시스템 연동 코드, 조직 고유 명칭은 **일절 포함하지 않습니다.**
> 데이터는 `backend/scripts/generate_sample_data.py`가 시드 고정 난수로 만든 합성 데이터이고,
> 그룹웨어·푸시·분석 플랫폼 연동은 같은 인터페이스의 대체 구현으로 바꿨습니다.

## 전체 흐름

```
 리드 유입                          리드                              기회                     보고
┌───────────────────────┐     ┌──────────────────────┐     ┌───────────────────────┐   ┌──────────────┐
│ 직원 제보              │     │ 미확인 → 연락함        │     │ 콜 → 예약 → 방문 → 선임 │   │ 부서별 현황   │
│  · 웹 폼              │ ──▶ │        → 관심있음      │ ──▶ │          └▶ 미선임(사유)│──▶│ 검토자 확인율 │
│  · AI 비서(자연어)     │     │ 보류 / 제외            │     │                       │   │ 선임 전환율   │
│ AI 자동 발굴           │     │ ──────▶ 배당 ─────────┼────▶│                       │   │ 미선임 사유   │
│  · 사건 기록 → LLM     │     └──────────────────────┘     └───────────────────────┘   └──────────────┘
└───────────────────────┘                ▲
                                         │ 사업자번호 → 정규화 법인명
                                  ┌──────┴───────┐
                                  │  고객 360     │
                                  └──────────────┘
```

저장소는 두 개로 나눴습니다. **MySQL이 원장**(상태 변경의 기준)이고, 목록·검색은
**Elasticsearch 단일 인덱스**가 맡습니다. 인덱스는 언제든 원장에서 다시 만들 수 있습니다.

## 설계에서 신경 쓴 지점

### 1. 정밀도 우선 2단계 추출·검증 — [`extraction/pipeline.py`](backend/app/extraction/pipeline.py)

리드는 검토자가 직접 전화를 거는 대상입니다. 엉뚱한 리드 한 건이 놓친 리드 한 건보다
비쌉니다(검토자가 시스템을 안 믿게 되니까요). 그래서 넓게 뽑고 엄격하게 거릅니다.

```
[1단계] LLM 추출 ── JSON Schema 로 출력 고정, 근거 문장(quote)을 원문 그대로 요구
   │
   ├─ 인용문이 원문에 없다 ─────────────▶ 폐기 (결정적 검사, LLM 을 믿지 않음)
   ├─ 현재 사건 범주와 같다 ─────────────▶ 폐기
   ├─ "우려·만약·가능성" 같은 가정 표현 ──▶ 폐기 (규칙 백업)
   ├─ "합의 완료·종결" 같은 종결 표현 ───▶ 폐기 (규칙 백업)
   ▼
[2단계] LLM 검증 ── 파생 쟁점 / 가정 / 이미 종결 / 인용문이 쟁점을 뒷받침하지 않음
   │                 → 하나라도 해당하면 폐기, 검증 호출이 실패해도 폐기
   ▼
 채택 (버린 후보도 사유와 함께 반환해 프롬프트 개선에 사용)
```

- 결정적으로 걸러낼 수 있는 건 검증 LLM을 부르기 전에 거릅니다. 비용도 줄고, LLM 판정이
  흔들려도 최소한의 기준은 지켜집니다.
- 모델은 사내(로컬) LLM이 기본이고, 로컬 컨텍스트를 넘는 긴 기록만 외부 API로 보냅니다
  ([`extraction/llm.py`](backend/app/extraction/llm.py)). LLM 없이 돌려 볼 수 있도록
  키워드 기반 대체 구현도 둡니다(`LOCAL_LLM_URL=offline`).

### 2. 재실행해도 한 건, 사람이 고친 건 안 건드린다 — [`ids.py`](backend/app/ids.py) · [`service.py`](backend/app/service.py)

발굴 배치는 재시도·재실행이 잦습니다.

- **리드 ID = 사건 + 범주**, **근거 ID = 요청 + 내용**의 해시입니다. 같은 입력이 몇 번
  들어와도 결과는 한 건으로 수렴합니다.
- 사람이 한 번이라도 고친 필드는 `human_edited`에 기록하고, AI 재발굴은 그 필드를 **절대
  덮어쓰지 않습니다.** 사람이 안 건드린 필드만 최신 추출값으로 갱신됩니다.
- **동시 편집**은 버전으로 비교합니다. 버전이 달라도 내가 바꾸려는 필드가 내가 본 값
  그대로면(= 서로 다른 필드를 고쳤으면) 병합하고, 같은 필드를 고쳤으면 409로 최신 상태를
  돌려줍니다.
- 계약으로 이어지지 않은 상담에서 나온 리드는 자동으로 `제외` 처리합니다.

### 3. 고객 연결 — [`customer_link.py`](backend/app/customer_link.py)

1순위 **사업자번호**, 2순위 **정규화한 법인명**입니다. `가온테크(주)`, `㈜가온테크`,
`주식회사 가온 테크`는 모두 같은 고객으로 묶입니다. 정규화 이름이 두 고객에 걸리면
잘못 붙이느니 연결하지 않고, 사람이 **수동으로 연결한 건은 자동 연결이 다시 건드리지
않습니다.**

### 4. 권한은 한 함수로 — [`permissions.py`](backend/app/permissions.py)

관리자 / 검토자 / 일반 직원 세 역할입니다. 화면 API와 **AI 비서의 도구 호출이 같은
`can()` 함수를 거칩니다.** 경로마다 권한 로직을 따로 두면, 언젠가 한쪽만 고쳐져서 비서가
화면에서는 볼 수 없는 리드를 읽어 주는 사고가 납니다. 테스트에서 화면 목록과 비서 응답이
같은지 직접 비교합니다.

- 푸시 알림에는 **본문을 싣지 않습니다.** 잠금화면에 사건 내용이 남지 않도록 lead_id만
  보내고, 내용은 로그인 후 앱에서 봅니다.
- 검토자마다 **검토 시작 시점**을 따로 둡니다. 늦게 합류한 검토자가 그 전에 쌓인 리드
  때문에 확인율이 낮게 보고되지 않게 하기 위해서입니다.

### 5. 필터를 빨리 바꾸면 "0건"이 뜨던 문제 — [`useLatestRequest.ts`](frontend/src/useLatestRequest.ts)

상태 탭을 빠르게 바꾸면 요청 여러 개가 연달아 나가는데, 늦게 도착한 **이전 요청의 응답이
최신 결과를 덮어써** 실제로는 리드가 있는데 "0건"이 보였습니다. 요청마다 순번을 매기고
현재 순번이 아닌 응답은 버리도록 고쳤고, 이 상황을 그대로 재현하는 회귀 테스트를
두었습니다([`LeadList.test.tsx`](frontend/src/LeadList.test.tsx)). 순번 검사를 빼면 이
테스트가 실패하는 것까지 확인했습니다.

### 6. 배포 순서: 매핑 → 배포 → 백필

인덱스 매핑은 `dynamic: strict`입니다([`es/leads_mapping.json`](backend/es/leads_mapping.json)).
매핑에 없는 필드는 색인 자체가 실패하므로 스키마가 조용히 불어나지 않습니다. 대신 새 필드를
쓰는 코드가 매핑보다 먼저 나가면 색인이 깨지기 때문에, 항상 **매핑 반영 → 코드 배포 →
[`scripts/backfill.py`](backend/scripts/backfill.py)로 백필** 순서를 지킵니다.
로컬용 메모리 인덱스도 같은 strict 동작을 흉내 냅니다.

## 실행

```bash
# backend
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]" uvicorn
python -m scripts.generate_sample_data          # 합성 데이터 (SQLite)
LOCAL_LLM_URL=offline uvicorn app.main:app      # LLM 없이 실행
pytest                                          # 26 tests

# frontend
cd frontend
npm install
npm run dev                                     # http://localhost:5173
npm test
```

운영 구성은 환경변수로 바꿉니다: `DATABASE_URL`(MySQL), `ES_URL`, `LOCAL_LLM_URL`,
`EXTERNAL_LLM_URL` / `EXTERNAL_LLM_KEY`, `LOCAL_MAX_CHARS`.
